# DESIGN_DECISIONS — 왜 이렇게 설계했나

이 문서는 TAP-LegalRAG의 주요 설계 결정을 **"어떤 문제가 있었고 → 무엇을 정했고 → 다른 선택지는 왜 버렸고 → 무엇을 대가로 치렀고 → 어떻게 확인하나"** 순서로 기록합니다.
처음 읽는 분에게는 구조를 이해하는 지름길이고, 후속 연구에서는 "이 결정을 바꿔도 되는가"를 판단하는 기준이 됩니다.

| # | 결정 | 한 줄 이유 |
|---|---|---|
| D1 | 검색과 판정을 다른 부품으로 | 틀렸을 때 원인을 나눠 볼 수 있어야 한다 |
| D2 | 판정을 P·T·A 세 축으로 | 축별 효과를 따로 재야 한다 |
| D3 | 결정을 세 가지로(답변·확인 요청·보류) | 애매할 때 "중간 답"이 가장 쓸모 있다 |
| D4 | P·T는 질문 속 인용에만 적용 | 검색된 현행 조문까지 흔들면 멀쩡한 답이 깨진다 |
| D5 | 판정은 규칙 기반·결정론적 | 행정 판단은 재현·설명 가능해야 한다 |
| D6 | 결정 경로를 하나로 | 평가한 코드와 쓰는 코드가 같아야 한다 |
| D7 | 무거운 의존성·네트워크 없음 | 재현성과 보안 |
| D8 | 정답 기준을 세 가지로 나눠 보고 | 한 기준만 쓰면 결론이 기준에 끌려간다 |
| D9 | 평가 동결과 수치 자동 대조 | 숫자를 보고 기준을 바꾸지 않기 위해 |
| D10 | 공개판을 따로 추출 | 저작권 자료·내부 자료·개인 정보를 구조적으로 막기 위해 |

## D1. 검색과 "답해도 되는가"를 다른 부품으로 나눈다

- **문제:** 검색 기반 답변이 틀렸을 때, 검색이 근거를 못 찾아서인지, 찾은 근거를 잘못 믿어서인지 구분할 수 없었다.
- **결정:** 검색(`retrieval/`)과 판정(`gate.py`)을 분리하고, 둘 사이는 데이터 계약(`models/`)으로만 주고받는다.
- **버린 대안:** 검색 점수가 낮으면 보류하는 단일 임계값 방식. 검색 점수는 "관련도"이지 "답해도 되는가"가 아니어서, 관련도는 높지만 시점이 어긋난 조문을 걸러내지 못한다.
- **대가:** 부품이 늘어 구조가 복잡해진다.
- **확인 방법:** 검색 성능(E2)과 판정 성능(E3)을 따로 보고한다. 검색이 약해도(R@5 0.372) 판정 효과를 별도로 측정할 수 있다.

## D2. 판정을 P·T·A 세 축으로 나눈다

- **문제:** 연구행정 질의의 위험은 성격이 다르다. 출처가 불분명한 것, 번호가 개정으로 밀린 것, 기관마다 답이 다른 것은 서로 다른 원인과 처방을 가진다.
- **결정:** 출처(P), 시점(T), 적용대상(A)을 독립된 검사로 만들고 설정 파일(`configs/`)로 켜고 끌 수 있게 했다.
- **버린 대안:** 하나의 "신뢰도 점수"로 합치는 방식. 점수가 낮다는 것만 알 뿐 무엇을 확인해야 하는지 사용자에게 말해 줄 수 없다.
- **대가:** 세 축이 서로 겹치는 경우의 우선순위를 규칙으로 정해야 한다.
- **확인 방법:** 축을 하나씩 끈 절제 실험(B4−P, B4−T, B4−A). 결과적으로 효과는 주로 A에서 나왔고, P·T는 이 데이터에서 아직 순이득이 아니었다. 이 사실을 숨기지 않고 보고한다.

## D3. 결정을 세 가지로 낸다 — 특히 "확인 요청"

- **문제:** "답한다/거부한다"만 있으면 애매한 경우 둘 다 나쁜 선택이다. 무조건 답하면 오답, 무조건 거부하면 쓸모가 없다.
- **결정:** ANSWER(근거를 붙여 답) · CONFIRM(후보와 이유를 보여 주고 확인 요청) · ABSTAIN(보류)으로 낸다. 기관 유형이 답을 가르면 묻거나(ASK) 유형별로 나눠 보여 준다(BRANCH).
- **버린 대안:** 낡은 조문 번호를 시스템이 알아서 새 번호로 고쳐 답하는 방식을 **현행에도 같은 번호가 있는 경우까지** 적용하는 것(rc2까지). "제64조 제2항"은 밀린 번호이면서 현행에도 같은 번호가 있어, 자동 교정이 오히려 틀릴 수 있었다. rc3부터 이 경우는 후보 두 개를 제시하는 CONFIRM으로 바꿨고, 옛 번호가 현행에 더는 없는 경우에만 전제 교정(CORRECT)을 낸다.
- **대가:** 확인 요청이 늘면 담당자 부담이 늘 수 있다. 실제 업무에서 이 부담이 받아들일 만한지는 측정하지 않았다(사용성 평가 미실시).
- **확인 방법:** E3에서 결정 분포와 "잘못된 보류" 수를 함께 보고한다.

## D4. P·T 검사는 "질문 속 인용"에만 적용한다

- **문제:** 첫 후보 버전(rc1)은 검색된 근거 전체에 P·T를 적용했다. 그러자 질문과 상관없는 현행 조문까지 "출처 불명"·"시점 의심"으로 흔들려 멀쩡한 답이 깨졌다.
- **결정:** rc2부터 P·T는 사용자가 질문에 직접 쓴 인용에만 적용한다. 검색으로 가져온 현행 조문은 코퍼스가 이미 출처와 판본을 보장한다.
- **대가:** 질문에 인용이 없으면 P·T는 아무 일도 하지 않는다.
- **확인 방법:** rc1→rc2 수치 변화와 원인을 [RESULTS](RESULTS.md)·[CHANGELOG](CHANGELOG.md)에 보존했다. 이전 수치를 지우지 않는다.

## D5. 판정은 규칙 기반이고 결정론적이다

- **문제:** 행정 판단은 나중에 "왜 그렇게 답했는가"를 설명할 수 있어야 한다. 생성형 모델을 판정에 쓰면 같은 질문에도 결과가 흔들리고, 판정 이유를 재현하기 어렵다.
- **결정:** 판정 단계에는 LLM을 쓰지 않는다. 같은 입력에는 같은 판정·같은 사유가 나오고, 매 결정에 판정 경로와 실행 ID를 남긴다.
- **버린 대안:** LLM에게 "이 근거로 답해도 되는지" 직접 묻는 방식. 유연하지만 재현과 감사가 어렵고, 평가 결과가 모델 버전에 따라 달라진다.
- **대가:** 규칙에 없는 표현(예: 괄호 없는 고시 이름)은 놓친다. 실제로 잘못된 보류 10건이 이 사전 누락에서 나왔다.
- **확인 방법:** 같은 설정 2회 실행 시 결과 파일 해시가 같은지 확인한다([PROCESS](PROCESS.md)).

## D6. 결정 경로를 하나로 묶는다

- **문제:** 평가 스크립트와 시연 코드가 각자 판정 로직을 가지면, 평가 점수가 실제 동작을 설명하지 못한다.
- **결정:** 평가·CLI·시연·MCP 도구가 모두 `law_rag.decide.decide_for_query`를 거친다. MCP 도구는 이 함수를 감싼 얇은 포장이다.
- **확인 방법:** MCP 도구 결과가 파이프라인 결과와 같은지 테스트로 확인한다(`tests/test_mcp_server.py`, MCP 설치 시).

## D7. 무거운 의존성과 네트워크를 쓰지 않는다

- **문제:** 임베딩 모델·벡터DB·외부 API에 기대면, 다른 사람이 같은 결과를 재현하기 어렵고 실행 중 데이터가 외부로 나갈 경로가 생긴다.
- **결정:** 런타임 의존성은 `pydantic` 하나다. 검색 기준선은 실제 Okapi BM25로 고정해 이후 단계 효과가 부풀려지지 않게 했다.
- **대가:** 자연어 질문 검색 성능이 낮다(R@5 0.372). 또 저장소에 고정한 법령 판본만 쓰므로 **실시간 법령 개정을 반영하지 못하고** 외부 서비스와 연계하지 않는다. 이 한계를 그대로 보고하고 개선은 로드맵(v1.2 공식 데이터 연계)에 둔다.
- **확인 방법:** `pip install -r requirements-lock.txt` 후 테스트가 Ubuntu·Windows CI에서 통과하는지 확인한다. 보안 측면은 [SECURITY](../SECURITY.md).

## D8. 정답 기준을 세 가지로 나눠 보고한다

- **문제:** 조문 인용 정답표는 LLM이 작성했다. 사람이 다시 보니 일부는 "앞뒤 문장만으로는 어느 법인지 특정할 수 없는" 문항이었다. 이런 문항에서 시스템이 보류한 것을 "틀렸다"고 채점하면 불공정하다. 반대로 사람 기준만 쓰면 설계자 판단에 기울 수 있다.
- **결정:** 같은 문항·같은 판정 로직을 세 기준으로 채점한다. gold(LLM 정답표, 동결) · final(설계자 최종판정) · context(문맥상 답할 수 있는 문항인가). context는 법령 귀속과 다른 과제라 2×2 표로 본다.
- **대가:** 결론이 하나로 깔끔하지 않다. 기준에 따라 순위가 바뀐다.
- **확인 방법:** `scripts/eval_provenance.py --labels` → `results/e1_label_views.json`, 테스트로 수치 고정. 이 "순위가 바뀐다"는 사실 자체를 핵심 발견으로 보고한다.

## D9. 평가를 먼저 동결하고, 문서 수치를 자동 대조한다

- **문제:** 결과를 본 뒤 채점 집합이나 지표를 바꾸면, 좋은 숫자는 나와도 그 숫자를 믿을 수 없다.
- **결정:** 채점 규칙을 [EVAL_SPEC](../specs/EVAL_SPEC_v1.md)에 먼저 적고 동결한다. 규칙 설계에 참고한 문항은 실행 전에 목록으로 기록하고 보조 분석에서 따로 뺀다. 문서 속 핵심 수치는 `scripts/sync_numbers.py`가 결과 JSON과 대조하고, 다르면 테스트가 실패한다.
- **대가:** 수치를 고치려면 결과를 다시 만들어야 해서 느리다.

## D10. 공개판을 허용목록으로 따로 추출한다

- **문제:** 개발 저장소에는 공공누리 제4유형 해설서 본문, 사람 검수 원본, 내부 작업 기록이 섞여 있다. 이를 "지울 것 목록"으로 관리하면 하나만 빠뜨려도 공개된다.
- **결정:** "넣을 것 목록(허용목록)"으로만 공개판을 만들고, 해설서 유래 텍스트를 제거한 뒤 다시 검사한다. 공개 저장소는 이전 이력 없이 새로 시작한다.
- **대가:** 공개판에서는 해설서가 필요한 평가 재계산 테스트를 건너뛴다([TESTING](TESTING.md)). 대신 결과 파일·평가 코드·라벨로 검토할 수 있게 했다.

## 후속 연구에서 다시 볼 질문

- 괄호 없는 고시 이름 같은 **사전 누락**을 규칙 추가로 고칠지, 학습형 인식기로 바꿀지 (D5의 대가)
- 확인 요청이 실제 담당자에게 **부담인지 도움인지** — 사용성 평가 필요 (D3의 대가)
- P·T 축이 순이득을 내려면 어떤 질문 분포가 필요한지 — FAQ와 독립된 새 질문셋 필요 (D2)
- 외부 조문 조회 도구와 결합했을 때 검색 개선 효과와 게이트 효과를 어떻게 분리 측정할지 (D1)
